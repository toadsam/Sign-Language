변수·목록·사전

# 설명용 Python 예시
frames = 80
tokens = [12, 7, 7, 91]
meta = {"clip": "예시_01", "frames": 80, "type": "WORD"}
print(meta["frames"])  # 80

=는 “같다”라는 비교가 아니라 오른쪽 값을 왼쪽 이름에 담는 명령입니다. tokens는 순서가 있는 목록이고, meta는 이름표로 값을 찾는 사전입니다. meta["frames"]는 frames라는 이름표의 값을 꺼냅니다. 실제 동작 좌표는 보통 Python 목록보다 계산에 유리한 NumPy 배열이나 PyTorch 텐서에 담습니다.

반복과 조건

# 설명용 예시: WORD만 남기기
words = []
for m in metas:
    if m["type"] == "WORD":
        words.append(m)

“메타 목록에서 하나를 꺼내 m이라고 부른다. 종류가 WORD이면 words에 추가한다.”라고 읽습니다. ==는 값이 같은지 비교합니다. 들여쓰기는 어떤 명령이 반복문·조건문 안에 속하는지 나타냅니다.

words = [m for m in metas if m["type"] == "WORD"]

위 한 줄은 방금 반복문을 압축해 쓴 리스트 내포입니다. 어려우면 항상 긴 반복문으로 풀어 읽으세요.

함수와 클래스

def token_count(frames, down=4):
    return frames // down

n = token_count(80)  # 20

def는 입력을 받아 계산을 하는 함수의 정의입니다. return은 결과를 돌려줍니다. //는 정수 나눗셈입니다. down=4는 따로 주지 않았을 때의 기본값입니다.

class MotionVQVAE는 모델의 구조와 행동을 묶은 설계도입니다. model = MotionVQVAE(...)는 그 설계도로 실제 객체를 만드는 일입니다. self.encoder는 “이 모델이 가지고 있는 인코더”입니다. PyTorch의 모델에서 model(x)는 내부 forward 계산으로 연결됩니다.

[T, 375]는 무엇이 달라진 건가요?

125 × 3 = 375입니다. 같은 숫자를 한 프레임당 긴 줄 하나로 펼쳤을 뿐입니다. 데이터 파일에는 [T,125,3]으로 저장하고, load_data가 모델에 주기 편하도록 [T,375]로 읽습니다. 계산을 위해 여러 클립 조각을 묶으면 앞에 배치 B가 붙어 [B,T,375]가 됩니다.

# 설명용 모양 예시
파일에서 읽음:       [80, 125, 3]
펼침:                [80, 375]
배치 축 하나 추가:   [1, 80, 375]
64프레임 창 32개:    [32, 64, 375]

float32는 소수 하나를 4바이트로 저장하는 형식입니다. 80프레임 한 클립의 좌표 값만 계산하면 80 × 125 × 3 × 4 = 120,000바이트입니다. 파일 헤더·메타데이터 용량은 별도입니다. 숫자를 펼쳐도 정보량은 줄지 않습니다. 시간 길이를 줄이는 것은 뒤에서 배울 인코더입니다.

  1. 첫 줄의 목록 내포는 meta.jsonl을 한 줄씩 읽어 설명 사전으로 바꿉니다.
  2. types가 있으면 WORD/SEN 중 원하는 종류만 남깁니다.
  3. per_signer가 있으면 사람별 표본을 뽑습니다. 작은 코드 확인에 쓰는 옵션입니다.
  4. 각 메타의 clip 이름으로 npy 파일을 찾아 읽습니다.
  5. reshape(-1, FEAT_DIM)에서 FEAT_DIM은 375입니다. 이 동작 배열을 m["x"]로 붙여 돌려줍니다.
확인: [32, 64, 375]의 32는 관절 수일까?

아닙니다. 한 번에 계산하는 동작 조각의 수, 배치 크기입니다. 각 조각은 64프레임이고 프레임마다 좌표 숫자 375개가 있습니다. 사람 32명이라는 뜻도 아닙니다.

실제 처리 순서

  1. 정면(F) 파일 선택·125점 추출

    조사한 5방향 파일의 3D 좌표가 같아서 정면만 읽었습니다. 상체·양손·얼굴을 정해진 순서로 합칩니다.

  2. 빠진 좌표 메우기

    좌표 셋이 모두 0인 관절을 결측으로 취급합니다. 앞뒤 정상 프레임 사이를 선형 보간합니다. 어떤 관절이 전 프레임 결측이면 코드에서는 0으로 채우므로 실제 위치를 알아낸 것으로 해석하면 안 됩니다.

  3. 단위 확인

    일부 원본은 m 대신 mm였습니다. 코드에서는 어깨너비 중앙값이 10을 넘으면 mm로 판단해 1000으로 나눕니다. 데이터에 맞춘 판별 규칙이지 완벽한 단위 검출기는 아닙니다.

  4. 작은 떨림 줄이기

    Savitzky–Golay 필터를 사용합니다. 기본은 가까운 5프레임을 보고 2차 곡선으로 추세를 잡습니다. 큰 오류를 자동으로 고치는 단계는 아닙니다.

  5. 손가락 뼈 길이 맞추기

    손가락 뼈가 매 프레임 늘었다 줄지 않도록 클립 내 길이의 중앙값을 사용합니다. 각 뼈의 방향은 유지하며 부모 관절부터 다시 연결합니다.

  6. 위치·방향·크기 정규화

    처음 10프레임의 평균 목 위치를 기준점으로 빼고, 어깨 방향으로 y축 회전한 뒤 어깨너비로 나눕니다.

  7. 움직임 구간 검출·저장

    처음 손목 자세에서 충분히 벗어난 구간을 active로 기록합니다. 정규화 좌표는 npy, 변환 정보는 meta에 저장합니다.

정규화를 숫자 하나로 이해하기

회전을 잠시 빼고 한 축만 보겠습니다. 사람 A의 목 위치가 2.0m이고 손이 2.32m, 어깨너비가 0.32m라면 (2.32 − 2.0) / 0.32 = 1입니다. 사람 B가 더 멀리 있고 더 커도, 손이 목에서 어깨너비만큼 떨어져 있으면 똑같이 1이 됩니다.

직접 계산 · 촬영 위치가 달라도 같은 상대 자세

원래 손 좌표 목 기준 손 좌표 정규화 후 1.00

손이 목에서 어깨너비 1배만큼 떨어진 상태를 유지하는 1차원 예시입니다. 실제 코드의 3D 회전은 생략했습니다.

  1. ref = x[:n_ref]: 처음 10프레임을 기준 자세 계산에 씁니다.
  2. origin: 그 구간의 목 좌표 평균입니다. 매 프레임 목을 따로 0으로 만드는 방식은 아닙니다.
  3. sh와 yaw: 어깨선이 x–z 평면에서 돌아간 각도를 구합니다.
  4. (x - origin) @ rot.T: 위치를 옮긴 다음 회전합니다. @는 행렬 곱입니다.
  5. scale: 클립 전체에서 양 어깨 거리의 평균을 구합니다.
  6. y / scale: 어깨너비를 1로 맞춥니다. origin/yaw/scale은 해석·단위 환산에 쓰도록 함께 반환합니다.

“목 원점”은 기준 목 위치를 뜻합니다. 사람이 시간에 따라 움직이는 작은 변화까지 모두 지우지는 않습니다. 정규화 후 1은 1미터가 아니라 어깨너비 1배입니다.

확인: 정규화 좌표 오차가 0.1이고 어깨너비가 0.32m이면 몇 mm일까?

0.1 × 0.32 × 1000 = 32mm입니다. 정규화 오차 자체를 mm라고 쓰면 단위가 틀립니다.

왜 라벨을 그냥 파일 순서대로 붙이면 안 될까요?

좌표가 48,000개 있어도 정면 라벨은 47,994개였고, 좌표에만 있는 것과 라벨에만 있는 것이 따로 있었습니다. 번호 순서대로 붙이면 한 파일 누락 이후 모든 정답이 밀릴 수 있습니다. clip 이름으로 맞춰야 합니다.

REAL02의 누락 55단어와 REAL25의 라벨 55단어가 번호·길이에서 비슷했지만, 같은 사람이라는 확인은 없었습니다. 그래서 재훈은 임의로 연결하지 않았습니다. 이 판단은 파일 수를 맞추는 것보다 학습 정답의 신뢰도를 우선한 것입니다.

30fps인 줄 알았는데 10fps라면?

영상 길이가 3초이고 좌표 프레임이 30개라면 실제 추출 속도는 10fps일 수 있습니다. 이를 30fps로 재생하면 1초에 끝나므로 3배 빨라집니다. 라벨의 2초 지점을 2×30=60번 프레임으로 바꾸면 파일 범위 밖이 됩니다.

dur_ratio = 영상 길이 / (좌표 프레임 수 / 30)
          = 3초 / (30 / 30초)
          = 3

라벨을 쓰는 모델의 조건:
label == "ok" 그리고 0.85 ≤ dur_ratio < 1.5

비율이 크면 프레임 속도·길이가 의심스럽다는 뜻입니다. 코드의 필터는 의심 클립을 걸러내는 조건이지, 원래 프레임 속도를 완벽하게 복원하는 기능은 아닙니다.

VQ와 받아쓰기가 라벨을 다르게 쓰는 이유

VQ는 입력 동작을 그대로 복원하도록 배웁니다. 정답은 그 동작 자체라 단어 이름이 없어도 학습 원리는 성립합니다. 받아쓰기는 단어·문장을 조건으로 토큰을 예측하므로 올바른 라벨이 필요합니다. 인식 모델 역시 동작의 단어 정답이 필요합니다. 그래서 같은 원본을 쓰더라도 학습 대상 조건이 다릅니다.

확인: 의문 라벨이 있으니 E5가 얼굴의 의문 표정도 만들까?

아닙니다. E5는 상체·손 55점만 학습하고 얼굴은 평균값으로 채웁니다. 라벨의 존재, 생성 모델의 조건 입력, 디코더가 얼굴 움직임을 만드는 능력은 각각 다른 조건입니다.

왜 프레임을 무작위로 섞어 나누지 않았을까요?

한 사람의 100프레임 중 80개를 학습, 20개를 시험에 넣으면 바로 옆의 거의 같은 자세를 이미 봤을 수 있습니다. 사람별 체형·습관도 양쪽에 남습니다. 새로운 사람의 동작을 표현할 수 있는지 보려면 사람 단위로 통째로 나누어야 합니다.

splits/full.json, full_sen.json, full_all.json은 각자가 매번 새로 뽑지 않고 같은 분할을 쓰기 위한 약속입니다. seed는 무작위 선택을 반복할 수 있게 하는 시작값이며 공정한 평가를 자동 보장하는 값은 아닙니다.

  1. excluded는 품질 제외 clip 이름을 빠르게 찾는 집합입니다.
  2. 제외 목록에 든 메타를 먼저 걸러냅니다.
  3. part는 “REAL03 → test”처럼 사람 이름에서 분할 이름을 찾는 사전입니다.
  4. out에 train/val/test 세 바구니를 만듭니다.
  5. 각 클립의 사람을 보고 해당 바구니에 넣습니다. 분할표에 없는 사람은 넣지 않습니다.
  6. 마지막에 세 목록을 돌려줍니다. 함수에는 라벨/길이·새 문장 조합을 거르는 조건이 없습니다.

“처음 보는 사람”과 “처음 보는 문장 조합”도 다릅니다

사람만 나눠도 같은 문장 순서는 학습에 있을 수 있습니다. 새 조합 생성 능력을 평가하려면 특정 gloss 열 전체를 생성 모델 학습에서 빼야 합니다. 이 프로젝트는 새 단어 열 50개와 별도 의문 항목 5개를 선정했습니다. 수행자마다 라벨이 조금 달라서 gloss 열 또는 문장 번호 또는 의문 항목 중 하나라도 해당하면 제외하는 규칙을 만들었습니다.

예시

학습에 “학교 → 가다”, “병원 → 있다”가 있고 시험에 “학교 → 있다”가 있다면, 단어를 처음 보는 시험이 아니라 아는 단어의 새 조합 시험입니다. 실제 선정 목록은 이 예시가 아니라 분할표의 heldout_sentences에 있습니다.

현재 인수인계 기준학습 대상 수
WORD: 품질 제외만 적용34,574
WORD: 라벨·길이도 적용34,501
SEN: 품질·라벨·길이 적용23,884
SEN: 새 조합 919개도 제외22,965
새 조합 test150클립 (학습 대상 아님)

E5는 SEN 추가 제외 58개와 새 조합 목록을 정하기 전에 학습됐습니다. “생성 모델에서 보지 않은 조합”이라고는 설명할 수 있지만, “VQ도 그 동작을 전혀 본 적 없다”고 말하면 틀립니다. 또한 현재 VQ 학습 코드는 중간마다 test 점수를 출력하고 실험 판단에도 이를 참고했습니다. 엄격한 최종 성능 주장에서는 val로 설정을 고르고 test를 마지막에 쓰는 절차와 이 제한을 구분해야 합니다.

확인: apply_split을 썼으면 문장 holdout도 자동으로 빠질까?

아닙니다. 함수가 처리하는 것은 exclude.clips와 수행자 또는 item 분할입니다. heldout_sentences 조건은 생성 학습 코드에서 별도로 적용해야 합니다. 이름이 “분할”이라고 모든 평가 조건을 처리한다고 추측하면 안 됩니다.

8장 · 모델의 첫 부분

인코더는 긴 동작을 압축된 설명으로 바꾸는 신경망입니다. 사람이 “팔이 올라가고 손가락이 접힌다”라고 설명하듯, 모델은 숫자로 된 특징을 만듭니다.

먼저 ‘학습하는 계산’이란?

아주 단순한 예로 출력 = 입력 × w가 있다면 w를 바꿀 때 출력이 달라집니다. 신경망은 이런 조절 가능한 숫자, 즉 가중치를 많이 가지고 있습니다. 처음부터 좋은 값을 아는 것이 아니라 복원 오차를 보며 조절합니다. 가중치는 프로그램의 구조와 달리 학습을 통해 달라지는 값입니다.

[B, 256, T/2]시간 길이 절반

[B, 256, T/4]시간 길이 다시 절반

E5 기본 특징 차원은 256입니다. 256은 코드북 칸 수 512와 다릅니다. 한 특징이 숫자 256개이고, 그 특징을 대표할 후보가 코드북에 512개 있는 것입니다.

  1. nn.Conv1d(in_dim, width, 3, padding=1): 시간 방향의 가까운 자세를 보고 특징을 계산합니다. 입력 채널은 좌표값들입니다.
  2. nn.ReLU(): 음수를 0으로 바꾸는 비선형 연산입니다. 여러 층이 복잡한 관계를 표현하도록 돕습니다.
  3. stride=2인 합성곱: 시간 방향으로 두 칸씩 진행하여 길이를 줄입니다. down_t=2라 두 번 수행합니다.
  4. resnet1d: 잔차 블록입니다. 입력에 학습한 변화를 더해 정보를 전달합니다.
  5. 마지막 합성곱은 특징의 채널 수를 code_dim으로 맞춥니다.
  6. self.net(x)는 쌓아 놓은 계산을 순서대로 실행합니다.
조금 더: “4프레임 = 토큰 하나”가 정확히 뜻하는 것

시간 길이가 4분의 1이 되므로 토큰 하나가 출력 시간에서 4프레임 간격을 담당한다는 뜻입니다. 합성곱은 주변 시간도 보기 때문에, 겹치지 않는 4프레임만 독립적으로 읽어서 토큰을 만든다는 뜻은 아닙니다. 디코더 역시 이웃 토큰 문맥을 함께 사용합니다.

잔차 블록의 x + f(x)는 이전 정보를 바로 전달하는 길을 남깁니다. dilation은 시간축에서 띄엄띄엄 떨어진 위치까지 볼 수 있게 하는 간격입니다. 처음에는 “가까운 프레임과 넓은 시간 문맥을 함께 본다”까지만 이해해도 됩니다.

확인: 80프레임을 인코딩한 뒤 특징 길이는? 토큰 후보는 몇 종류?

길이는 80÷4=20입니다. 각 위치의 특징은 기본 설정에서 256차원이고, 각 특징을 바꿀 코드북 후보는 512종입니다. 20, 256, 512는 각각 시간 길이·특징 차원·후보 종류 수입니다.

9장 · VQ의 핵심

비슷한 특징을
같은 번호로 부릅니다

Vector Quantization은 여러 숫자로 된 특징 벡터를, 준비된 대표 벡터 중 가장 가까운 것으로 바꾸는 일입니다.

색상표 비유

무한히 많은 색을 제한된 물감 세트로 표현한다고 생각해 보세요. 입력 색과 가장 가까운 물감 번호를 고릅니다. 수어 자모표는 색 대신 동작 특징을 비교합니다. 코드북은 그 대표 특징을 모은 표이고 토큰은 선택한 행 번호입니다.

대표가 512개이면 번호는 0~511입니다. 번호 47이 더 크거나 작은 동작을 뜻하지는 않습니다. 번호의 대소는 의미 순서가 아닙니다. 모델을 다시 학습하면 같은 번호가 다른 특징을 나타낼 수 있습니다.

직접 고르기 · 가장 가까운 대표는?

설명용 2차원·6개 코드 예시입니다. 실제 E5는 256차원·512개입니다. 움직이는 입력과 대표를 선으로 연결해 가장 가까운 후보를 표시합니다.

이 함수는 특징 x와 코드북의 모든 행 사이 거리를 계산하고, 가장 작은 거리의 번호를 반환합니다.

  1. x.pow(2).sum(1): 입력 특징의 제곱을 더합니다.
  2. x @ self.codebook.t(): 입력과 각 대표의 내적입니다. t()는 코드북의 행·열을 뒤집어 곱할 수 있게 합니다.
  3. 거리 식 ||x−c||² = ||x||² − 2x·c + ||c||²를 한꺼번에 계산합니다.
  4. dist.argmin(1): 가장 작은 거리의 값이 아니라 번호를 고릅니다.

대표 특징은 누가 정하나요?

사람이 “이 번호는 손 올리기”라고 이름을 붙인 것이 아닙니다. 학습 중 인코더가 만든 특징에서 시작하고, 그 대표를 선택한 특징들의 평균 방향으로 조금씩 옮깁니다. 이 코드에서는 EMA, 즉 과거 값을 많이 남기면서 새 정보를 조금 섞는 이동 평균을 씁니다. 기본 mu=0.99는 기존 통계 99%, 새 배치 통계 1%를 섞는 설정입니다.

일부 코드만 계속 선택되면 나머지는 배우지 못합니다. 이를 코드북 붕괴라고 부릅니다. 사용량이 부족한 코드를 현재 특징으로 다시 채우는 reset도 구현되어 있습니다.

사용률과 perplexity는 왜 둘 다 기록하나요?

사용률은 512칸 중 한 번이라도 등장한 칸의 비율입니다. perplexity는 얼마나 고르게 사용했는지를 요약합니다. 512칸을 모두 한 번씩 썼어도 대부분 한 칸만 반복하면 사용률은 높고 perplexity는 낮을 수 있습니다. ppl 208이 “208개만 사용했다”는 뜻은 아닙니다.

조금 더: argmin처럼 딱 고르는 연산은 어떻게 학습할까요?

번호 선택은 연속적으로 조금씩 변하는 계산이 아닙니다. 코드의 xq = x + (xq - x).detach()는 앞방향 계산에서는 선택한 대표 xq를 쓰되, 뒤로 학습 신호를 보낼 때는 x로 바로 전달하는 straight-through 방식입니다. 코드북 자체는 일반 가중치처럼 optimizer로 갱신하지 않고 EMA로 갱신합니다.

확인: “512개 자모로 3,000단어를 표현한다”는 말은 모순일까?

아닙니다. 토큰 하나가 단어 하나를 뜻하지 않습니다. 여러 토큰의 순서와 문맥으로 하나의 동작을 표현합니다. 글자 종류보다 단어 종류가 많은 것과 비슷하지만, 토큰에 사람이 정한 언어 의미가 있는 것은 아닙니다.

토큰을 하나씩 따로 복원해 붙이면 같은 결과일까요?

꼭 같지 않습니다. 디코더의 합성곱이 주변 토큰을 함께 보기 때문입니다. 토큰 격자는 한 토큰을 반복한 상황에서 어떤 모습이 나오는지 보여주는 시각화입니다. 실제 단어 속에서 그 토큰이 반드시 똑같은 4프레임 모양을 만든다는 보장은 없습니다.

80프레임, 125관절 형식이 나옵니다. 다만 움직임을 예측한 관절은 앞 55개이고 얼굴 70개는 평균 얼굴입니다. 출력 배열은 배치 1일 때 [1,80,375]입니다.

11장 · 학습 루프

복원해 보고, 차이를 재고,
다음에는 덜 틀리게 고칩니다

학습은 한 번의 마법 같은 변환이 아니라 작은 수정의 반복입니다. 한 반복에서 무엇이 바뀌는지 보면 긴 학습 코드도 읽을 수 있습니다.

학습 한 번의 순서

  1. 동작 조각 뽑기

    학습 클립에서 무작위로 64프레임 창을 잘라 배치를 만듭니다. 기본 batch=32입니다. 한 iteration이 전체 데이터를 한 번 다 봤다는 뜻은 아닙니다.

  2. 복원해 보기

    xh, commit, ppl, _ = model(x). x는 정답 동작, xh는 복원, commit은 인코더 특징과 대표 사이의 손실, ppl은 사용 분포입니다.

  3. 손실 계산

    위치·속도·손가락 상대좌표·commitment 손실을 섞습니다.

  4. 가중치 수정

    이전 gradient를 비우고, 오차를 줄일 방향을 계산하고, optimizer가 한 걸음 수정합니다.

  5. 기록·평가·저장

    몇 번마다 손실·사용률을 기록하고 복원 오차를 계산합니다. 중간 상태와 최종 모델을 저장합니다.

np.empty는 결과를 담을 자리를 마련합니다. 배치의 각 칸마다 클립 하나를 뽑고, 가능한 시작 프레임 s를 뽑아 x[s:s+window]를 넣습니다. torch.from_numpy는 NumPy 배열을 PyTorch 계산에 사용할 텐서로 연결합니다. 창보다 짧은 클립은 main에서 먼저 제외합니다.

왜 손실을 여러 개 쓰나요?

손실쉽게 말하면없으면 놓칠 수 있는 것
위치 pos관절이 원래 위치에 가까운가팔·손의 전체 위치
속도 vel다음 프레임으로 움직이는 변화가 비슷한가시간에 따른 떨림·동작 변화
손 상대 hand손목에 비해 손가락 모양이 비슷한가손 전체 위치가 맞아도 손가락이 뭉개지는 문제
commit인코더 특징이 선택한 대표에서 너무 멀어지지 않는가인코더·코드북 표현의 불안정

view로 375개 값을 다시 관절·좌표로 나눕니다. nj만큼만 써서 E5에서는 얼굴을 손실에서 제외합니다. x4[:,1:] − x4[:,:-1]는 연속 프레임의 차이입니다. 물리적 m/s로 환산한 값이 아니라 정규화 좌표의 프레임 간 변화입니다.

코드의 위치·속도·손 손실은 단순 L1이 아니라 Smooth L1입니다. 작은 차이 부근은 부드럽게, 큰 차이는 상대적으로 덜 급격하게 증가하도록 계산합니다. 부위 가중치는 손 2, 몸 1을 기본으로 두고 평균으로 정규화합니다.

# 실제 train.py 학습 루프의 핵심과 같은 순서
loss = pos + 0.5 * vel + 1.0 * hand + 0.02 * commit
opt.zero_grad()   # 지난 반복의 gradient 비우기
loss.backward()  # 손실을 줄일 가중치 변화 방향 계산
opt.step()       # 가중치 한 걸음 수정

위 계수는 코드의 기본 설정입니다. 실행 옵션이 바뀌면 계수도 바뀔 수 있습니다. 이 전체 손실값은 학습 목적함수이며, 보고서의 손 mm와 같은 단위·숫자가 아닙니다.

한 번씩 배우기 · 조절 숫자 w 하나만 있는 작은 모델

입력 2에 대해 정답 6을 만들고 싶습니다. 출력은 2×w입니다.

제곱 오차와 단순 경사하강법으로 만든 설명용 계산입니다. 실제 VQ 학습·AdamW·EMA는 실행하지 않습니다.

더 알아보기: learning rate, epoch, checkpoint

learning rate는 한 번에 얼마나 고칠지 정하는 크기입니다. 너무 크면 지나치고 너무 작으면 느릴 수 있습니다. warmup은 처음부터 큰 보폭을 쓰지 않고 조금씩 늘리는 방식입니다.

iteration은 배치로 한 번 업데이트한 횟수입니다. epoch는 보통 전체 학습 데이터를 한 차례 본 양을 뜻합니다. 이 코드는 무작위 창을 계속 뽑으므로 “20만 iteration = 데이터를 20만 번 전부 읽음”은 틀립니다.

checkpoint는 모델뿐 아니라 optimizer와 난수 상태·현재 반복 수 등을 저장합니다. 이어 학습할 때 진행 상태를 복구합니다. 최종 model.pt와 중간 ckpt.pt는 목적이 다릅니다.

확인: 손실이 줄었으니 처음 보는 사람에게도 잘할까?

학습 손실 감소만으로는 모릅니다. 훈련 자료를 외울 수도 있습니다. 분리된 사람의 복원 오차와 손모양을 확인해야 합니다. 코드 사용률·다른 데이터 구간도 함께 봐야 합니다.

모델을 학습하는 일과, 학습된 모델로 데이터를 토큰화하는 일은 다릅니다. 토큰화에서는 가중치를 고치지 않습니다.

단어와 문장을 다르게 자르는 이유

단어 클립은 시작과 끝에 손을 내리고 기다리는 구간이 있습니다. 이것까지 단어의 특징으로 배우면 단어를 이어 붙일 때 매번 손을 내릴 수 있습니다. 그래서 WORD는 active 앞뒤 4프레임만 여유로 남깁니다. SEN은 단어 사이의 움직임을 배워야 하므로 전체 구간을 남깁니다.

  1. T: 실제 클립 길이입니다.
  2. WORD이면 active 시작에서 4를 빼고 끝에는 4와 1을 더합니다. active 끝이 포함형이라 Python의 끝 제외 슬라이스로 바꿀 때 +1이 필요합니다.
  3. max와 min으로 파일 범위를 넘지 않게 합니다.
  4. SEN이면 s=0, e=T로 전체를 선택합니다.
  5. (e-s)//down*down으로 길이를 4의 배수로 줄입니다. 끝의 최대 3프레임이 잘릴 수 있습니다.

직접 계산 · 전체 구간을 쓸 때

SEN처럼 전체를 사용하는 예시입니다. 번호는 넣지 않고 토큰 칸 수만 표시합니다. WORD에는 먼저 active 자르기가 있습니다.

tokens_e5.json 안에는 무엇이 있나요?

// 구조 설명용 예시. 실제 토큰 열을 복사한 것이 아닙니다.
{
  "vq_version": "v0.3-e5",
  "nb_code": 512,
  "down": 4,

예시의 36~116은 끝 제외 80프레임이므로 토큰 20개입니다. 실제 파일의 tokens는 문자열 없이 정수로만 구성됩니다. 각 클립에 item/signer/type과 구간이 있지만 label·dur_ratio·gloss는 없습니다. 따라서 학습 조건을 모두 적용하려면 메타도 읽어야 합니다.

실제 산출물과 확인 범위

  • WORD 48,000개 + SEN 32,000개 = 80,000클립을 변환했습니다.
  • 토큰 개수 범위는 WORD 3~46개, SEN 16~85개였습니다.
  • 8만 개 전체에 대해 메타 대응·번호 범위·프레임 길이와 토큰 수의 관계를 점검했습니다.
  • 36개 표본은 실제 좌표를 다시 인코딩해 저장 토큰과 일치하는지 확인했습니다. 8만 개 전체를 재인코딩한 검사는 아닙니다.

현재 gen/tokenize.py는 vq_version을 자동 출력하지 않습니다. 기록에 따르면 v0.3-e5 문자열은 만들어진 파일에 별도로 추가했습니다. “버전 관리 요구사항이 있다”와 “생성 코드가 자동 보장한다”는 다른 말입니다.

확인: 토큰 파일이 8만 클립이면 8만 개를 전부 학습에 써도 될까?

아닙니다. 그 안에는 평가·검증 사람과 품질 제외 대상도 있습니다. 분할표·메타의 라벨/길이·문장 holdout을 적용한 뒤 학습 목록을 만들어야 합니다.

관절 위치 오차

같은 프레임·같은 관절의 원본과 복원 좌표 사이 직선 거리를 구합니다. 3D에서는 x·y·z 차이를 제곱해 더한 뒤 제곱근을 구합니다. 정규화 좌표의 거리에 norm.scale × 1000을 곱하면 mm입니다. 손의 오차는 양손 42점에서 평균낸 값입니다.

손가락 상대 오차는 각 손의 손목을 빼서 손목 기준으로 비교합니다. 손 전체가 조금 밀렸지만 손모양은 맞는 경우와 손가락 형태 자체가 틀린 경우를 구분하는 데 도움을 줍니다. 이 값도 수어 의미 정확도 자체는 아닙니다.

클립 평균과 프레임 평균

평균 방식이 다르면 숫자가 달라집니다

짧은 클립 A: 10프레임·평균 10mm. 긴 클립 B: 평균 30mm.

A/B는 설명용 가상 클립입니다. 긴 클립에 더 많은 비중을 줄지에 따라 결과가 달라집니다.

vq/train.py → evaluate는 먼저 클립별 오차를 구하고 클립들의 평균을 냅니다. vq/eval_clips.py는 프레임을 단어·전환·앞뒤 구간으로 나누어 모아 평균을 냅니다. E5 summary의 혼합 test 손 28.2mm와 SEN 별도 평가의 28.1mm는 같은 표본·집계가 아닙니다.

왜 단어 구간·전환·대기를 따로 봤나요?

손을 내리고 기다리는 프레임은 복원하기 쉬울 수 있습니다. 전체 평균만 보면 정작 수어를 하는 구간의 오차를 가릴 수 있습니다. 라벨의 시작·끝 시각을 사용해 의미 있는 단어 구간과 단어 사이 전환을 따로 측정했습니다.

처음에는 모든 프레임을 앞뒤(2)로 두고, 라벨 구간을 단어(0)로 표시한 다음 두 단어 사이 빈 구간을 전환(1)으로 표시합니다. 이미 단어 구간인 곳은 전환으로 덮어쓰지 않습니다. 구간 라벨이 부정확하면 이 평가도 영향을 받습니다.

DTW는 다른 속도를 맞춰 비교하는 방법

같은 단어도 한 사람은 느리게, 다른 사람은 빠르게 할 수 있습니다. 프레임 번호끼리 바로 비교하면 속도 차이도 큰 오차가 됩니다. DTW는 시간축에서 서로 대응시킬 위치를 찾아 비교합니다. B1의 52.7mm는 55관절 DTW 거리이고, E5의 손 28.1mm는 복원 프레임의 손 위치 오차입니다. 이 둘을 그대로 빼서 “24.6mm 개선”이라고 말하면 안 됩니다.

평가에서 아직 남은 것

코드 사용률이 높고 좌표 오차가 작아도 수어를 읽을 수 있는지는 따로 봐야 합니다. 역할표에는 평가 사람의 단어 10개 손모양 식별, 승현의 읽는 모델을 이용한 역번역 보존율 확인이 남아 있습니다. 생성 결과는 생성 모델이 나온 뒤 B1·B2와 같은 조건으로 비교해야 합니다.

확인: E5 얼굴 오차 35.0mm를 “얼굴 생성 성능”이라고 발표해도 될까?

안 됩니다. E5의 얼굴은 평균 얼굴입니다. 움직이는 얼굴을 학습한 결과가 아니므로 얼굴 생성 성능으로 해석하지 않습니다. 부위·모델 조건을 숫자와 함께 설명해야 합니다.

계약은 파일과 함수의 모양을 정하는 약속입니다. 다른 사람이 네 코드를 전부 이해하지 않아도 이어 붙일 수 있게 합니다.

계약넘기는 것받는 쪽이 확인할 것
① 동작 데이터npy·meta·공통 분할표·좌표계같은 관절 순서와 단위, 같은 평가 사람, 품질·라벨 조건

버전과 해시를 왜 같이 기록하나요?

버전 이름은 사람이 읽는 표지입니다. 서로 다른 파일에 같은 이름이 붙을 수도 있습니다. SHA-256 해시는 파일 내용으로 계산한 지문입니다. 인수인계 때 해시가 일치하면 파일이 같은지 확인할 수 있습니다. 해시가 일치한다고 학습 품질이 좋다는 뜻은 아닙니다.

인수인계가 끝나는 조건

  1. 팀원이 공용 경로에 접속해 필요한 파일을 읽는다.
  2. 받은 파일 해시와 버전을 대조한다.
  3. 디코더를 불러와 유한한 float32 좌표와 예상 모양이 나오는지 확인한다.
  4. 필터 적용 후 학습/검증/평가 목록과 수를 확인한다.
  5. 실행 결과와 사용할 버전을 팀에서 확인한다.

공용 서버에 팀원별 handoff 링크를 만든 기록은 있습니다. 팀원들의 최초 접속·수령 실행과 v1 승인까지 완료됐다는 증거는 이 브랜치에서 확인되지 않았습니다.

현재 자료에서 조심해서 읽을 두 부분

간단 안내와 상세 점검표의 차이

지헌용 간단 안내에는 토큰+분할표만으로 시작할 수 있다고 적혀 있지만, 상세 점검표와 계약은 메타의 label·dur_ratio 조건도 요구합니다. 올바른 학습 목록에는 메타가 필요합니다. 네 브랜치의 gen/train_word·train_sentence에는 그 필터가 없습니다. 지헌의 다른 최신 브랜치에서 고쳤는지는 별도 확인 대상입니다.

v1 후보와 v1 완료: 발표 초안의 “E5로 간다”는 방향과 실제 v1 동결 완료는 다릅니다. 사용률 기준은 넘었지만, 손 오차 개선을 어떤 데이터에서 판정할지, 단어 10개 손모양 식별, 팀 승인을 확인해야 합니다.

지금까지의 역할 상태

  • 완료 근거 있음: WORD/SEN 정리, 고정 분할, E1·E2·E4a·E4b·E5, 토큰 제작·점검, B1, 격자, 발표 초안, 서버 배치 기록.
  • 완료 근거 없음: E3, 256개 비교 실험, v1 최종 동결·팀 수령 실행, 정식 인식 모델로 역번역 보존율.
  • 네 담당과 팀 통합을 구분: 생성 모델 본 학습·추론 API·웹캠·앱 완성은 각 담당자의 진행과 결합해야 합니다.

먼저 AI Hub의 단어 48,000개와 문장 32,000개 클립을 정리했습니다. 좌표의 단위, 귀·눈 오류, 프레임 속도 문제를 검사했고, 학습과 평가에 같은 사람이 섞이지 않게 분할표를 고정했습니다.

모델은 동작의 시간 길이를 4분의 1로 줄여 특징을 만들고, 512개 대표 특징 중 가까운 번호로 바꿉니다. 디코더는 그 번호를 다시 동작으로 만듭니다. E5는 몸과 손만 학습하며 얼굴은 평균 얼굴입니다.

실험에서는 코드북을 크게 하거나 얼굴을 함께 넣는 것만으로 손 오차가 좋아지지 않았습니다. 단어만으로 학습하면 문장의 전환을 잘 표현하지 못해 문장도 함께 학습했습니다. E5에서 문장 전체 손 오차가 37.3에서 28.1mm로 줄었습니다.

현재 8만 클립의 토큰과 디코더, 공통 분할표를 준비하고 점검했습니다. v1 확정, 손모양 확인, 팀원 수령·실행과 정식 역번역 평가는 남아 있습니다.”

여기에 “내가 직접 판단한 것”을 하나 붙이세요. 예를 들어 귀 좌표의 수리 범위, REAL25 라벨을 임의 연결하지 않은 이유, 단어와 문장 성능의 균형을 고려해 E5를 후보로 선택한 이유입니다. 코드를 AI와 함께 작성했다는 사실과 결과를 검증·판단하는 책임을 구분해서 설명하면 됩니다.

125, 375, 375, 165, 20, 20, 80입니다. 이 예시는 이미 사용할 구간이 80프레임으로 정해졌다고 가정합니다. WORD는 토큰화 전 active 자르기가 있으므로 원본 전체가 80프레임이라는 조건만으로 토큰이 항상 20개라고 할 수는 없습니다.

스스로 답할 질문 10개

1. VQ는 무엇을 정답으로 배우나요?

입력 동작 자체를 복원 정답으로 배웁니다. 단어 이름을 맞히는 분류와 다릅니다.

2. 125점과 375차원은 왜 둘 다 등장하나요?

관절 125개에 x/y/z 세 좌표가 있어 375개 숫자입니다. 같은 정보를 나누어 보거나 펼쳐 본 모양입니다.

3. “토큰 47 = 학교”라고 정의할 수 있나요?

아닙니다. 동작 특징 대표의 번호입니다. 여러 단어에서 나타날 수 있고, 특정 단어와 자주 함께 나온다는 통계가 단어 뜻 자체는 아닙니다.

4. 손이 부드러워 보이면 수어가 정확한가요?

아닙니다. 평활화는 중요한 손가락 변화까지 약하게 만들 수 있습니다. 위치 오차, 손가락 상대좌표, 의미 식별을 함께 확인해야 합니다.

5. 코드북 크기를 1024로 늘리면 왜 더 좋다고 단정할 수 없나요?

표현 후보가 늘어도 학습 데이터·최적화가 충분하지 않을 수 있고 생성 모델이 골라야 하는 종류도 늘어납니다. 이번 E4a에서는 손 오차가 오히려 커졌습니다.

6. test 사람을 학습에 넣지 않았다면 평가에 아무 문제 없나요?

가중치 학습에서 분리한 것은 중요하지만, test 결과를 계속 보며 후보를 고르면 선택 과정이 test에 맞춰질 수 있습니다. 검증과 최종 시험의 역할도 분리해야 합니다.

7. E5는 최신 제외 2,008개를 모두 적용해 학습했나요?

아닙니다. SEN 58개 추가 제외 전에 학습했습니다. 현재 전달하는 분할표와 E5의 당시 학습 조건이 다른 부분입니다.

8. tokens_e5.json과 E1 디코더를 같이 쓰면 왜 안 되나요?

번호가 가리키는 코드북 벡터가 다릅니다. 같은 번호라도 다른 특징으로 해석하므로 동작이 잘못 복원될 수 있습니다.

9. 36클립 재인코딩 일치가 무엇을 보장하나요?

선택한 36개에서 좌표→토큰 변환이 저장 파일과 일치함을 보여줍니다. 전체 8만 개 재인코딩 일치나 의미 정확성을 입증한 것은 아닙니다. 전체에는 별도의 구조 검사를 했습니다.

10. 지금 다음으로 해야 할 개발보다 먼저 할 학습은?

한 클립의 배열 모양을 끝까지 따라가고, E4b→E5의 선택 이유를 자신의 말로 설명하는 것입니다. 이후 이해가 부족한 파일 하나를 골라 입력·처리·출력을 손으로 적어 보세요.
